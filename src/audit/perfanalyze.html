성능시험 결과 분석

응답시간 데이터로 백분위수·TPS 등 성능 지표를 분석합니다.

한 줄에 응답시간(ms) 하나씩 붙여넣으세요. p95/p99는 SLA 판정에 중요합니다. 모든 처리는 브라우저에서만 이루어집니다.

성능시험 결과 분석 사용 안내

무엇을 하는 도구인가

부하시험이나 단건 측정에서 얻은 응답시간(ms) 목록을 붙여 넣으면 샘플 수, 평균, 최소/최대, 표준편차, p50·p90·p95·p99 백분위수, 단일 스레드 기준 추정 처리량(TPS)을 계산합니다. 가장 크게 표시되는 값은 p95입니다. 성능 목표를 "평균 1초 이내"보다 "95%의 요청이 1초 이내"처럼 백분위로 잡는 경우가 많아, 판정에 바로 쓸 수 있는 숫자를 앞에 둔 것입니다.

언제 쓰나

  • 성능시험 결과서를 쓰기 전에 도구가 내보낸 응답시간 열을 빠르게 요약할 때
  • 감리에서 사업자가 제출한 원시 데이터로 보고서의 p95·최대 응답시간을 다시 계산해 볼 때
  • 운영 로그에서 뽑은 특정 거래의 응답시간에 튀는 값이 섞여 있는지 확인할 때
  • 튜닝 전후 같은 시나리오의 결과를 나란히 비교할 때

사용 방법

  1. 응답시간을 ms 단위로 한 줄에 하나씩 붙여 넣습니다. 쉼표나 공백으로 구분해도 됩니다.
  2. 입력하는 즉시 결과 표가 갱신됩니다.
  3. 먼저 샘플 수가 넣은 건수와 같은지 확인하고, 평균·중앙값·p95를 비교해 봅니다.

결과 해석

백분위수는 정렬한 값에서 순위 = 올림(p% × 건수)번째 값을 그대로 고르는 방식이라 항상 실제 관측값 중 하나가 나옵니다. 추정 처리량은 1000 ÷ 평균 응답시간으로, 요청을 하나씩 순서대로 보내는 스레드 하나가 1초에 처리할 수 있는 건수입니다. 기본 예시 13건을 보면 평균 359.2ms, 중앙값 145ms, p90 880ms, p95와 p99는 둘 다 2200ms, 표준편차 566.8ms, 추정 처리량 2.8 TPS입니다. 대부분은 100~200ms대인데 880ms와 2200ms 두 건이 평균을 두 배 넘게 끌어올리고 있습니다. 이런 결과라면 평균만 보고하면 실제 사용자 경험을 잘못 전달하게 되니, 느린 두 건이 특정 시점(시작 직후, GC, 배치 실행)에 몰려 있는지 원본 로그를 확인하는 것이 다음 단계입니다.

주의할 점

추정 처리량은 동시성을 고려하지 않은 값이라 실제 시스템 TPS가 아닙니다. 스레드나 가상 사용자가 N개면 대략 N배가 되지만, 서버가 포화되면 그대로 늘지 않습니다. 샘플이 100건 이하이면 p99는 최댓값과 같아지므로 의미 있게 보려면 충분한 건수가 필요합니다. 표준편차는 입력 전체를 모집단으로 보고 계산합니다. 빈 줄과 숫자가 아닌 값(예: 120ms처럼 단위가 붙은 값, 헤더 글자)은 샘플에서 빠지므로, 단위가 붙은 로그라면 숫자만 남긴 뒤 붙여 넣고 샘플 수가 원본 건수와 같은지 확인하세요. 오류 응답이나 시간대별 변화는 이 숫자 목록만으로 알 수 없습니다.

자주 묻는 질문

p95를 SLA 기준으로 쓰는 이유가 뭔가요?
평균은 소수의 매우 느린 요청에 쉽게 흔들리고 최댓값은 우연한 한 건에 좌우됩니다. p95는 "거의 모든 사용자가 겪는 최악의 수준"을 안정적으로 보여 줘서 목표 기준으로 쓰기 좋습니다.
응답시간 분포·통계 분석 도구와 p95 값이 다릅니다.
그 도구는 백분위 위치가 두 값 사이에 걸리면 두 값의 평균을 쓰고, 이 도구는 순위에 해당하는 실제 값 하나를 고릅니다. 건수가 적을수록 차이가 커지며, 어느 방식인지 보고서에 함께 적어 두면 혼선이 없습니다.
