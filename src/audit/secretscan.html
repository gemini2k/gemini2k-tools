하드코딩 시크릿·키 탐지

코드·설정에 노출된 API 키·비밀번호 등 시크릿을 찾아 줍니다.

정규식 휴리스틱 기반 참고용 점검입니다. 모든 분석은 브라우저에서만 이루어지며 입력은 전송되지 않습니다.

하드코딩 시크릿·키 탐지 도구 사용 안내

무엇을 하는 도구인가

소스코드나 설정 파일에 API 키, 비밀번호, 개인키가 그대로 적혀 있으면 저장소가 유출되거나 공개되는 순간 바로 악용됩니다. 이 도구는 붙여넣은 텍스트를 줄 단위로 읽어 대표적인 시크릿 형식을 찾고, 찾은 값은 앞 4자리와 끝 3자리만 남기고 가려서 보여 줍니다(8자 이하면 첫 글자만 표시).

찾는 형식은 6가지입니다. AWS Access Key(AKIA로 시작하는 20자), Google API Key(AIza로 시작), Slack 토큰(xoxb-, xoxp- 등), PEM 개인키 블록(-----BEGIN … PRIVATE KEY-----), JWT(eyJ로 시작하는 점 3분할 토큰), 그리고 password·passwd·pwd·secret·token·api_key 뒤에 =나 :로 6자 이상의 값이 붙은 경우입니다.

언제 쓰나

  • 깃 저장소에 커밋하기 전에 application.properties, .env, 설정 스크립트를 점검할 때
  • 외주 개발 산출물 인수 시 소스에 운영 계정 정보가 남아 있는지 볼 때
  • 장애 대응 중 로그나 설정을 메신저·이슈에 붙이기 전에 민감값이 섞였는지 확인할 때
  • 보안 점검에서 하드코딩된 비밀번호 항목의 근거를 빠르게 찾을 때

사용 방법

  1. 입력칸의 예시를 지우고 점검할 코드나 설정 내용을 붙여넣습니다.
  2. 입력 즉시 결과창에 "n건 발견:"과 목록이 표시됩니다.
  3. 각 줄의 L번호로 원본 위치를 찾아 값을 제거하고, 환경변수나 비밀 관리 도구로 옮깁니다.

결과 해석

결과 형식은 "L줄번호 [유형] 마스킹된 값"입니다. 한 줄이 두 규칙에 동시에 걸리면 두 번 나옵니다. 기본 예시 5줄은 7건으로 집계되는데, GOOGLE_API_KEY 줄과 slack_token 줄이 각각 전용 규칙과 "하드코딩 비밀" 규칙에 함께 걸리기 때문입니다. db.password 줄은 P@ss****024처럼 가려져 표시됩니다. 건수보다 줄 번호 기준으로 몇 곳을 고쳐야 하는지 세는 편이 정확합니다.

이미 저장소에 올라간 키가 발견됐다면 파일에서 지우는 것만으로는 부족합니다. 커밋 이력에 남아 있으므로 해당 키를 폐기하고 새로 발급하는 것이 먼저입니다.

주의할 점

  • 정규식 휴리스틱이라 위 형식이 아닌 시크릿(postgres://user:pass@host처럼 URL에 섞인 비밀번호, 다른 클라우드 사업자의 키, 변수명이 pw처럼 짧은 경우 등)은 놓칠 수 있습니다.
  • 반대로 password = "changeme" 같은 예시값이나 문서 속 샘플도 잡히므로 실제 값인지는 사람이 판단해야 합니다.
  • 입력은 브라우저 밖으로 나가지 않지만, 화면에는 마스킹 전 원문이 입력칸에 그대로 보이니 공유 화면에서는 주의하세요.

자주 묻는 질문

저장소 전체를 검사할 수는 없나요?
이 도구는 붙여넣은 텍스트만 봅니다. 저장소 전체와 커밋 이력까지 보려면 gitleaks 같은 전용 스캐너를 CI에 붙이는 것이 맞습니다.
BEGIN PUBLIC KEY나 인증서도 잡히나요?
아닙니다. 공개키와 인증서는 노출돼도 문제가 없으므로 PRIVATE KEY 블록만 찾습니다.
