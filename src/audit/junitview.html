JUnit/xUnit 결과 뷰어

테스트 결과 XML을 통과/실패/스킵으로 집계하고 실패를 보여 줍니다.

JUnit/xUnit 표준 XML(testsuite/testcase)을 인식합니다. 파일은 업로드되지 않고 브라우저에서만 파싱됩니다.

JUnit/xUnit 결과 뷰어 사용 안내

무엇을 하는 도구인가

자동화 테스트가 만들어 내는 JUnit 형식 결과 XML을 붙여 넣으면 testcase 요소를 하나씩 읽어 통과·실패·오류·스킵 건수, 통과율, 총 소요시간을 계산하고 실패한 케이스의 클래스·테스트명·메시지를 표로 뽑아 줍니다. JUnit 형식은 Java 진영뿐 아니라 pytest, Jest(jest-junit), Maven Surefire, Gradle 등 여러 도구가 내보낼 수 있는 사실상의 공통 형식이라, CI 서버에 접근하지 않고도 결과 파일만으로 상황을 파악할 수 있습니다.

언제 쓰나

  • 개발사가 제출한 단위시험 결과 파일을 받아 실제 통과율을 직접 확인할 때
  • 감리에서 "단위시험 100% 통과"라는 보고와 결과 파일의 건수가 맞는지 대조할 때
  • CI 화면을 볼 수 없는 폐쇄망에서 빌드 산출물로 받은 결과만 검토할 때
  • 야간 회귀 테스트에서 실패한 케이스 목록을 결함관리 시스템에 옮길 때

사용 방법

  1. 결과 XML(예: TEST-*.xml, junit.xml, report.xml)을 텍스트 편집기로 열어 전체를 복사합니다.
  2. 입력란에 붙여 넣으면 0.3초 뒤 자동으로 집계됩니다. testsuites로 여러 스위트를 묶은 파일도 그대로 넣으면 됩니다.
  3. 상단 통과율과 막대, 그 아래 실패·오류 목록을 확인합니다.

결과 해석

판정 순서는 failure 요소가 있으면 실패, 없고 error 요소가 있으면 오류, 둘 다 없고 skipped가 있으면 스킵, 아무것도 없으면 통과입니다. 통과율은 통과 ÷ 전체 testcase 수이며 스킵도 분모에 들어갑니다. 기본 예시는 4건 중 통과 2, 실패 1(login_fail, "expected 200 got 500"), 스킵 1이라 통과율 50%, 소요시간 0.60s로 나옵니다. 실패(failure)는 단언문이 틀렸다는 뜻이라 기능 결함일 가능성이 높고, 오류(error)는 예외나 환경 문제로 테스트가 끝까지 돌지 못한 경우가 많아 원인을 다르게 봐야 합니다. 스킵이 많으면 통과율이 낮아지므로, 보고서에서는 스킵 사유를 함께 적어 두세요.

주의할 점

건수는 testsuite 요소의 tests·failures 속성이 아니라 실제 testcase 요소를 세어 계산합니다. 두 값이 다르면 결과 파일이 중간에 잘렸거나 일부가 합쳐지지 않았을 수 있습니다. 소요시간은 testcase의 time 속성을 더한 값이라 스위트 준비 시간은 빠집니다. 메시지는 failure·error 요소의 message 속성 앞부분만 보여 주고 스택 트레이스 본문은 표시하지 않습니다. 테스트 결과가 좋다는 것이 테스트 범위가 충분하다는 뜻은 아니니 커버리지 결과와 함께 보세요.

자주 묻는 질문

"XML 파싱 오류"가 납니다.
파일 앞부분에 로그 문자열이 섞였거나 복사할 때 끝부분이 잘린 경우가 대부분입니다. 첫 줄이 <?xml 또는 <testsuite로 시작하는지, 마지막 닫는 태그까지 들어갔는지 확인하세요.
여러 결과 파일을 한 번에 볼 수 있나요?
한 번에 하나의 XML만 해석합니다. 여러 파일을 합치려면 각 파일의 testsuite 부분을 <testsuites> … </testsuites> 안에 차례로 넣어 하나의 문서로 만든 뒤 붙여 넣으면 됩니다.
