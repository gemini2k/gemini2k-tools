JSON 스키마 검증기

JSON 데이터가 JSON Schema(draft-04~2020-12) 규칙에 맞는지 확인하고, 어긋난 부분을 알려 줍니다.

오픈소스 Ajv(MIT, ajv-validator/ajv)를 자체 호스팅합니다. 이메일·날짜 등 format 검증과 draft-04·06·07, 2019-09, 2020-12 스키마를 지원합니다. 모든 처리는 브라우저에서만 이루어집니다.

JSON 스키마 검증기 사용 안내

무엇을 하는 도구인가

JSON Schema와 데이터를 나란히 넣으면 Ajv 8로 스키마를 컴파일해 데이터가 규칙에 맞는지 검사하고, 어긋난 곳을 경로와 메시지로 모두 나열합니다. 첫 오류에서 멈추지 않고 전체 오류를 모으며(allErrors), email, date, date-time, uri, uuid, ipv4 같은 format 키워드도 검사합니다(ajv-formats). 스키마의 "$schema" 주소를 보고 draft-04, draft-06, draft-07, 2019-09, 2020-12 중 맞는 규칙으로 자동 전환하며, $schema가 없으면 draft-07로 처리합니다. 결과 제목 옆에 실제로 적용된 버전이 표시됩니다.

언제 쓰나

  • API 요청 본문이 명세의 스키마를 통과하는지 서버에 보내기 전에 확인할 때
  • 새로 쓴 스키마가 의도대로 잘못된 데이터를 걸러 내는지 일부러 틀린 예시로 시험할 때
  • 설정 파일 검증 오류가 났을 때 어느 필드가 문제인지 찾을 때

사용 방법

  1. 왼쪽 'JSON Schema'에 스키마를, 오른쪽 '검증할 데이터'에 데이터를 넣습니다.
  2. 입력하는 즉시 검사되며, [검증하기]로 다시 실행할 수도 있습니다.
  3. 통과하면 초록 안내가, 실패하면 위반 개수와 목록이 나옵니다.

결과 해석

기본 예시는 2건 위반으로 나옵니다. /age — must be >= 0은 age가 minimum: 0을 어겼다는 뜻이고, /email — must match format "email"은 이메일 형식이 아니라는 뜻입니다. 앞의 경로는 데이터 안 위치를 JSON Pointer 형식으로 /items/0/id처럼 표시합니다(items 배열 첫 번째 요소의 id). 필수 키가 빠진 경우처럼 객체 전체에 대한 오류는 (root)로 나옵니다. 예를 들어 데이터에서 name을 지우면 (root) — must have required property 'name'이 추가됩니다. 허용되지 않은 키가 있으면 must NOT have additional properties ('키이름')처럼 문제의 키를 괄호 안에 덧붙입니다. 메시지는 Ajv가 내는 영어 원문입니다.

주의할 점

  • 버전은 $schema 주소로만 판단합니다. 2020-12 전용 키워드(prefixItems 등)를 쓰면서 $schema를 빼면 draft-07로 처리되어 그 키워드가 무시되니, 버전을 꼭 적어 두세요. 위 다섯 가지가 아닌 주소를 적으면 메타스키마를 찾을 수 없다는 스키마 정의 오류가 납니다.
  • 스키마에 모르는 키워드(예: example, 사내 확장 키워드)가 있어도 오류로 막지 않고 건너뜁니다. 오타 난 키워드도 조용히 무시되므로, 기대한 위반이 안 잡히면 키워드 철자를 먼저 확인하세요.
  • 외부 URL로 된 $ref는 내려받지 않으므로 해석되지 않습니다. 같은 스키마 안의 #/definitions/..., #/$defs/... 참조만 쓸 수 있습니다.
  • format은 형식 검사일 뿐 실제 존재 여부를 확인하지 않습니다. email을 통과해도 받을 수 있는 주소라는 뜻은 아닙니다.

자주 묻는 질문

스키마가 없는데 검증하고 싶어요.
JSON 스키마 생성기로 예시 데이터에서 초안을 만든 뒤 여기 붙여넣고 다듬으면 됩니다.
스키마에 없는 키가 있는데 통과돼요.
JSON Schema는 기본적으로 정의되지 않은 키를 허용합니다. 막으려면 객체에 "additionalProperties": false를 추가하세요.
